# WhatsApp Group Lead-Finder — Flow Architecture

A niche-targeted discovery + scoring engine that finds public WhatsApp group invite links matching an ICP (industry + geo), ranks them with an LLM, and surfaces them in a dashboard.

---

## 1. Inputs

| Input | Example |
|---|---|
| Industries | `["AI agency owners", "Marketing agency owners", "SaaS"]` |
| Locations (include) | `["US", "UK", "Dubai"]` |
| Locations (exclude) | `["India", "Indian"]` |
| Platforms | `["reddit", "web"]` (LinkedIn, X deferred) |

---

## 2. Tech Stack

| Layer | Choice | Job |
|---|---|---|
| Frontend | Next.js | Campaign builder + leads dashboard |
| API | FastAPI | Campaign CRUD, status polling, results listing |
| Worker | arq (asyncio-native) | Runs the 7-stage pipeline async |
| DB | Postgres | Campaigns, leads, queries, runs, scores |
| Cache / Queue | Redis | Job queue + URL cache + rate limiters |
| LLM | OpenAI (`gpt-4o-mini`) | Query generation + lead scoring |
| Search | Serper | Google search results |
| Scrape | Firecrawl + asyncpraw | Web pages + Reddit |

## 3. High-Level Architecture

```
┌──────────────┐  POST /campaigns   ┌────────────┐
│   Next.js    │ ─────────────────> │  FastAPI   │
│              │ <───── id ──────── │            │
└──────────────┘                    └─────┬──────┘
       │ poll /campaigns/{id}             │
       │ GET /leads?campaign_id=          │ enqueue job
       v                                  v
┌──────────────┐                    ┌─────────────┐
│   Postgres   │ <───────────────── │ Redis Queue │
│ campaigns    │                    └─────┬───────┘
│ leads        │                          │
│ queries      │                    ┌─────v────────────────┐
│ runs         │                    │ Worker (arq)         │
└──────────────┘                    │  ┌────────────────┐  │
       ^                            │  │ ICP → queries  │  │
       │ writes                     │  │ Serper search  │  │
       └────────────────────────────│  │ URL router     │  │
                                    │  │ Reddit/Firecr. │  │
                              ┌─────│  │ regex extract  │  │
                       Redis  │     │  │ OpenAI score   │  │
                       cache <┘     │  └────────────────┘  │
                                    └──────────────────────┘
```

Key idea: **FastAPI does not run the pipeline.** It enqueues a job, returns immediately, and the worker drives the stages. Frontend polls for progress.

## 4. Postgres Schema

```sql
campaigns
  id, name,
  industries          text[],
  locations           text[],
  negative_locations  text[],
  platforms           text[],         -- ['reddit', 'web']
  status,                             -- 'queued' | 'running' | 'done' | 'budget_exceeded'
  created_at, completed_at

queries                                -- generated by LLM from campaign
  id, campaign_id, query_text, source_platform, status

search_results
  id, query_id, url, title, snippet, position, status

leads                                  -- the actual product
  id,
  invite_id          UNIQUE,           -- "AbCdEf123" from chat.whatsapp.com/AbCdEf123
  source_url, source_text,
  detected_geo, language,
  relevance, geo_fit, engagement, total_score,
  campaign_id,
  first_seen, last_scored_at

url_cache                              -- saves Firecrawl credits
  url PRIMARY KEY, markdown, fetched_at
```

`invite_id UNIQUE` does cross-campaign dedup automatically — same group found by 5 campaigns = 1 row, scored per ICP.

## 5. The 7-Stage Pipeline

| # | Stage | Input | Output | Cost/unit | Concurrency |
|---|---|---|---|---|---|
| 1 | Generate queries | campaign | N query strings | 1 LLM call | sequential |
| 2 | Search | each query | 10 results | 1 Serper credit | 10 concurrent |
| 3 | Snippet pre-filter | results | hit / needs-fetch | free | in-memory |
| 4 | Route + fetch | needs-fetch URLs | markdown content | Reddit free / FC 1 credit | 5 concurrent |
| 5 | Extract | content | (invite_id, context) | free | in-memory |
| 6 | Score | new leads | scored leads | 1 LLM call per 10 leads | 5 concurrent |
| 7 | Finalize | scored leads | ranked output | free | sequential |

### Pipeline flow with checkpoints

```
campaign.status = "queued"
        ↓
worker picks up job → status = "generating_queries"
        ↓
┌──────────────────────────────────────────────┐
│ STAGE 1: GENERATE QUERIES                    │
│  OpenAI: ICP → 30 queries                    │
│  INSERT queries (status='pending')           │ ◄── checkpoint
└──────────────────────────────────────────────┘
        ↓ status = "searching"
┌──────────────────────────────────────────────┐
│ STAGE 2: SEARCH (asyncio.gather, n=10)       │
│  for each pending query:                     │
│    Serper.search(q) → 10 results             │
│    INSERT search_results                     │ ◄── checkpoint
│    UPDATE query.status = 'searched'          │
└──────────────────────────────────────────────┘
        ↓ status = "extracting"
┌──────────────────────────────────────────────┐
│ STAGE 3: SNIPPET PRE-FILTER (free yield)     │
│  for each search_result:                     │
│    regex chat.whatsapp.com on snippet        │
│    HIT  → mark needs_fetch=false             │
│    MISS → mark needs_fetch=true              │
└──────────────────────────────────────────────┘
        ↓
┌──────────────────────────────────────────────┐
│ STAGE 4: ROUTE + FETCH (asyncio.gather, n=5) │
│  for each needs_fetch URL:                   │
│    if cached in url_cache → use it           │
│    elif reddit.com  → asyncpraw              │
│    elif facebook/insta → mark skipped        │
│    else → Firecrawl /scrape                  │
│    UPSERT url_cache(url, markdown, fetched_at) ◄── checkpoint
│    UPDATE search_result.status = 'fetched'   │
└──────────────────────────────────────────────┘
        ↓
┌──────────────────────────────────────────────┐
│ STAGE 5: EXTRACT (in-memory)                 │
│  for each fetched content:                   │
│    regex chat\.whatsapp\.com/[A-Za-z0-9]+    │
│    capture ±200 chars context                │
│    INSERT lead                               │ ◄── checkpoint
│      ON CONFLICT (invite_id) DO UPDATE       │
│      SET last_seen = now()                   │
└──────────────────────────────────────────────┘
        ↓ status = "scoring"
┌──────────────────────────────────────────────┐
│ STAGE 6: SCORE (asyncio.gather, n=5)         │
│  batch leads in groups of 10                 │
│  for each batch:                             │
│    OpenAI(ICP, leads) → scores               │
│    UPDATE leads SET relevance, geo_fit, ...  │ ◄── checkpoint
└──────────────────────────────────────────────┘
        ↓ status = "done"
┌──────────────────────────────────────────────┐
│ STAGE 7: FINALIZE                            │
│  campaign.completed_at = now()               │
│  emit webhook (optional)                     │
└──────────────────────────────────────────────┘
```

## 6. Negative Location Handling (applied twice)

1. **In query gen** — pass exclusions into the LLM prompt → uses `-india -indian` operators in Google queries to remove most matches up front.
2. **In scoring** — OpenAI sees `source_text` + ICP, penalizes wrong-geo leads with `geo_fit: 0`. Cheap insurance for what slips through stage 1.

Example query the LLM generates:

```
site:reddit.com whatsapp group "AI agency" US -india
"marketing agency owners" whatsapp community Dubai -indian
site:reddit.com "agency owners" whatsapp join UK
```

## 7. State Machines (drives resumability)

**Query lifecycle**
```
pending → searching → searched → extracted
             └─ failed (after 3 retries)
```

**Search result lifecycle**
```
new → needs_fetch / snippet_hit → fetching → fetched / fetch_failed / skipped → extracted
```

**Lead lifecycle**
```
new → scored
       └─ stale (re-score on next run)
```

Every stage is **idempotent**. If the worker crashes mid-stage 4, restart picks up "all search_results where status = needs_fetch" and continues. No state lives in worker memory — Postgres is the source of truth.

## 8. Concurrency Model

```python
serper_sem    = asyncio.Semaphore(10)   # Serper handles plenty
reddit_sem    = asyncio.Semaphore(3)    # 100/min ÷ 60s = 1.6/s, comfortable
firecrawl_sem = asyncio.Semaphore(5)    # don't melt the plan
openai_sem    = asyncio.Semaphore(5)

async def fetch_url(url):
    if 'reddit.com' in url:
        async with reddit_sem:
            return await reddit_fetch(url)
    else:
        async with firecrawl_sem:
            return await firecrawl_fetch(url)

# stage 4 driver
await asyncio.gather(*[fetch_url(u) for u in urls])
```

Each external service has its own semaphore. One slow Firecrawl call won't block Reddit calls.

---

## 9. Error Handling

| Failure | Strategy |
|---|---|
| OpenAI 429 / 500 | Exponential backoff, 3 retries |
| Serper 429 | Backoff respecting `Retry-After` header |
| Firecrawl "site not supported" | Mark `fetch_failed`, don't retry (permanent) |
| Reddit 403 / rate limit | Backoff; refresh OAuth token if persistent |
| Worker crash mid-stage | Resume from last DB checkpoint |
| Whole campaign timeout (>30 min) | Mark `partial`, return what's scored |

Per-URL failures **never abort the campaign**. A failed scrape just means one fewer lead, not a stopped pipeline.

## 11. Caching

Two caches in Redis:

```
url_cache:    url        → (markdown, fetched_at)    TTL 7 days
query_cache:  query_text → search_results            TTL 1 day
```

Same campaign run twice → almost free. Two campaigns sharing 70% of queries → only pay for the 30% delta. Realistic: **40–60% credit savings** after week 2.

## 12. Worker Pattern (MVP)

```python
@arq.task
async def run_campaign(campaign_id):
    await stage_1_generate_queries(campaign_id)
    await stage_2_search(campaign_id)
    await stage_3_prefilter(campaign_id)
    await stage_4_fetch(campaign_id)
    await stage_5_extract(campaign_id)
    await stage_6_score(campaign_id)
    await stage_7_finalize(campaign_id)
```

Each stage commits to DB before the next. Worker dies → re-enqueue same `campaign_id`, it picks up where it left off (each stage queries DB for "what's still pending"). **Stage-as-job** pattern is a later optimization once you actually need fine-grained retry / parallel campaign processing.

## 13. Realistic Timing (per campaign, 100 queries / ~1000 URLs)

| Stage | Time |
|---|---|
| 1. Generate 30 queries | ~3s |
| 2. Search × 30 (10 concurrent) | ~5s |
| 3. Prefilter | <1s |
| 4. Fetch ~600 URLs (5 concurrent) | ~3–6 min |
| 5. Extract | ~2s |
| 6. Score ~150 leads (batches of 10) | ~30s |
| 7. Finalize | <1s |
| **Total** | **~5–8 min** |

Frontend polls `/campaigns/{id}/status` → returns `{stage, progress: 234/600, leads_so_far: 47}`.

## 15. Build Order

1. **Stage 1 + 2 + 3** end-to-end — verify Serper queries return useful URLs. *(1 day)*
2. **Stage 4 + 5** — verify regex catches real WhatsApp links. *(1 day)*
3. **Stage 6** — verify scoring is sensible. *(½ day)*
4. **FastAPI shell + Postgres + Redis + worker.** *(2 days)*
5. **Next.js campaign builder + leads table.** *(2–3 days)*

**~1 week to working v1.** Then iterate on query quality, scoring rubric, UI.

> **v1 rule:** single-tenant (you only). Don't build auth/multi-tenant until you've validated leads are good with one happy user.
